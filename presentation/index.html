Three things that actually bit us
1 · The model was eating base64
"QLStkeuFHrk=" → 5293.57
Bigtable returned packed IEEE-754 doubles. Gemini didn't error — it quietly made things up. ~150 lines of "working" code never ran.
2 · Parallel wasn't parallel
Sync tools run on the event loop unless a thread pool is configured — and adk web doesn't configure one. Two "concurrent" tools ran back to back. Nothing failed. It was just silently twice as slow.
3 · Iceberg rejects row-level security
We chose an open table format for interoperability. It cost us BigQuery-native governance. A trade-off to make deliberately — not discover in production.

Every one of these was silent. None threw an exception.

100 seconds. If tight, do only #1 — it's the best story. #1 lesson for the room: tool output is an API contract with a NON-DETERMINISTIC client. Spare card if the room is infra-heavy: gemini-3.6-flash publishes only to `global`. Our .env said us-central1, so every model call would have 404'd. Invisible until the tests started loading .env.

The lesson

NL2SQL doesn't fail by writing broken SQL.
It fails by writing valid SQL
against a metric nobody defined.

The semantic layer isn't documentation — it's the control plane. If “override rate” isn't defined once, centrally, the model will define it for you. Differently. Every time.
Slow down here. This is the single most transferable idea in the talk, and it applies to every NL2SQL / "chat with your data" product any of them will be asked to evaluate.

A prompt is a request
“Only show this manager their own store” — evaluated by a probabilistic system. Injection routes around it.
A row access policy is a control
Enforced by BigQuery beneath every tool. The model can be fully compromised and still not read another tenant's rows.

Proven, not assumed: granting one store collapsed visibility from 65,368 rows to 1,233.

60 seconds, and it's an infra-audience slide — lean into it. The identity changes at deploy time: locally the agent runs as ME, with my permissions. In the runtime it runs as a service account that has never been granted anything. RLS turning a permission gap into an empty result instead of a 403 is the nastiest variant of that, because the failure is indistinguishable from "there is no data". Observability, without an observability project
One plugin registration
BigQueryAgentAnalyticsPlugin streams every prompt, response, tool argument, latency and token count over the Storage Write API. Background batcher — agent latency is not coupled to BigQuery.
320 events · 24 turns · 4 tools · 23 auto-created views
Two defaults that quietly break it
location="US" → write stream resolves to a different BigQuery instance than a single-region dataset.

table_id="agent_events" → views are named after the table, so nothing downstream lines up.
Wired fail-open: if telemetry can't start, the agent still serves traffic. Losing observability should never become an outage.
40 seconds. The infra framing: you did not stand up a logging pipeline, a collector, or a dashboards project. You registered a plugin and got a queryable event table with 23 views over it. The cost is a BigQuery dataset. If asked about PII: content is captured, so this dataset inherits the sensitivity of your prompts — treat it as production data, not as logs.

Takeaway
1 · The model is a router
It holds no data and no permissions of its own. Everything hard about this was infrastructure.
2 · Authorisation belongs below the model
Prompts are requests. Row access policies are controls.
3 · Grounding and refusal are features
The system that says “I don't know which store you mean” is the one you can put in front of an auditor.
4 · Every failure here was silent
Base64 as numbers · zero rows instead of 403 · a wrong store ID · NaN as an error. None threw. You do not find these by watching. You find them by measuring.
